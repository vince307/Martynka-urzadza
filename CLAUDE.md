# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Bystrow" (until 2026-10-31 "Martynka urządza"; the repo, the font name, the IndexedDB database `martynka` and the `martynka:*` storage keys keep the old name so saves survive) is a math-practice + room-decorating game for children in grades 1–3 (inspired by Gossip Harbor's loop): the child solves age-appropriate maths tasks in rounds of 5 to earn stars, then spends stars on renovation tasks and picks one of 3 visual variants per furniture slot. On first launch the game asks the child's age and maps it to a curriculum stage (E1–E6 = grade × semester); difficulty then adapts per skill. There is no merge board anymore. Target is a landscape tablet, touch only, installable offline PWA. No backend; progress is saved locally.

**`Martynka-urzadza.md` is the authoritative design and plan (in Polish).** Read it before starting any milestone. It defines the data model, task screen, room flow, save format, PWA requirements, asset naming and the M0–M8 milestones.

**`docs/ZADANIA.md` is the maths task catalogue** (stages E1–E6, ordered steps, task types with number ranges, generator data model). Task generators and `src/data/curriculum/` must follow it. `docs/zrodla/` holds reference notes from the analysed textbooks: never copy textbook tasks into the game, only generate original tasks of the same types. That folder is gitignored (local only, the repository is public); do not reference its contents from committed files.

```bash
npm run icons        # redraw the app icons in public/icons/ from the Bystrow logo (python3 with Pillow 12.1.0; deterministic)
npm run font         # rebuild public/fonts/MartynkaNext.ttf (plain zero) from designs/martynka-maths-A-v1/fonts/AtkinsonHyperlegibleNext.ttf with scripts/make-font.py (python, fontTools 4.61.1 pinned, byte-identical output)
npm run art          # convert the art kits' PNGs (designs/, local only: maths kit, salon-v2 pack, martynka-fox-guide-v1) to WebP in public/assets/ (needs cwebp, and python3 with Pillow 12.1.0 + numpy 2.4.3 for the board recolour)
npm run typecheck    # tsc --noEmit (src/, tests/, scripts/); Vite does not type-check during dev or build
npm run lint         # ESLint 10 flat config (eslint.config.mjs): recommendedTypeChecked + module-boundary rules, --max-warnings 0
npm test             # vitest run (tests/**/*.test.ts); single file: npx vitest run tests/addSub.test.ts; by name: npx vitest run -t "<name>"
npm run sample -- E3 # (any stage E1–E6) print 3 tasks per curriculum step of a stage and report violations (exit 1 on any); --seed N, --count N
npm run check:deploy -- https://martynka-urzadza.pl <sha7> [--redirect-from <old domain>]  # post-deploy smoke (target address https://bystrow.ariom.cloud/graj/, old one valid until the move) (headers, manifest, precache, build id); in the agent sandbox prefix NODE_USE_ENV_PROXY=1
npx playwright test   # local browser e2e (tests/e2e/, Chromium): builds and serves on port 4398 itself; never in CI; outside the agent sandbox (Chromium cannot start in it)
```

ESLint enforces the module boundaries (`src/core` without Phaser or browser globals; `src/data` imports from `core` only `core/text/*` and types) and `tests/lint-boundaries.test.ts` checks those rules on synthetic sources, so a config regression fails the suite. Every pull request runs `.github/workflows/ci.yml` (lint, typecheck, tests, `sample` E1–E6, build); the deploy workflow lints before building. Generators are pure `(skill, rng) => Task` functions registered in `src/core/tasks/registry.ts` next to their params parsers (parsers reject infeasible data); each gets a 1000-draw test (20 seeds × 50, `tests/helpers.ts`) that replays failures by seed, and `tests/contentInvariants.test.ts` checks every skill of every stage (hint arithmetic, bounds, variety, degenerate shares), every noun used in a prompt must be in `src/data/nouns.ts` (the validator and `tests/wordTemplates.test.ts` check agreement for 0–100), `src/data/` may import only `src/core/text/*` and types from `core/`, and `scripts/sample.ts` runs `node --import tsx` because Node's type stripping cannot resolve extension-less imports.

Vite configs live in `vite/config.dev.mjs` and `vite/config.prod.mjs`, both built on `vite/config.shared.mjs` (`base: '/graj/'` = `APP_BASE`: the landing page owns `/` on bystrow.ariom.cloud, so the manifest `start_url`/`scope`, `sw.js` and its scope (`import.meta.env.BASE_URL` in `src/pwa/registerServiceWorker.ts`) all stay under `/graj/`; hashed bundles in `_app/`, Phaser in its own chunk, PWA plugin). Files in `public/` are served at the base, so Phaser loader paths are relative (`assets/...`, never a leading `/`), manifest icons are relative to the manifest, `index.html` uses `%BASE_URL%`, and e2e specs open the game with `page.goto('./…')` (baseURL ends in `/graj/`); `public/assets/` is never cached as immutable (only `/_app/*` is), and the precache globs cover js, css, html, png, webp, ogg, m4a, woff2 and ttf, so every asset is precached (no lazy chunks; the Phaser loader may load a room's art after boot, from the precache) while the service worker uses `clientsClaim`.

## Target architecture (from the plan)

- `src/core/`: pure TypeScript game logic (task generators, curriculum/mastery/round/placement, rooms, save/migrations, seeded rng) with **no Phaser imports**, so it can be tested with vitest.
- `src/data/`: all content and tuning as data (curriculum stages E1–E6, word-problem templates, logic puzzles, rooms/slots/renovation tasks, `balance.ts` numbers, `pl.ts` strings). Adding a room, curriculum step or task template should only touch `data/` plus assets.
- `src/scenes/`: Boot, Welcome (age + warm-up), Task (round of 5 tasks), Room, House (the cross-section of the house) and UI (an overlay with the star counter and the tasks/room switch). Scenes only render state and forward player actions to `core/`. Reusable widgets (keypad, answer tiles, clock, ruler, coins, number line) live in `src/ui/widgets/`.
- `src/storage/idb.ts`: IndexedDB persistence, plus JSON export and import.
- Base resolution is 1920×1080 with `Phaser.Scale.FIT` + `CENTER_BOTH`. Slot coordinates in room data are in this space.
- The save state is versioned (`SaveState.version`) and needs a migration function in `core/save.ts`. Autosave runs on state changes (debounced about 500 ms) and on `visibilitychange`.

## Working rules (from the plan, section 14)

- **Content changes need a teacher read.** Any PR touching `src/data/` or `src/core/tasks/generators/` runs `npm run sample -- <stage> --count 6` and reads every task of the changed steps as a Polish primary-school teacher would: numeral agreement and the accusative after verbs ("ma 1 naklejkę"), verb gender matching the name, sensible context, hints that teach the school method without giving the result away in the first step, close but unambiguous distractors, every new noun in `src/data/nouns.ts` with its accusative in the context, prompts of 1–3 sentences. The validator only knows dictionary nouns, so this read is what caught the two critical content bugs in S-02. The checklist is in `.github/pull_request_template.md`.

- Implement milestones in order, one milestone per commit or PR. After each one, verify the production build and offline behaviour.
- Write logic in `core/` with tests first, then the scene.
- Scenes must not contain balance numbers or player-facing text. Those come from `data/`.
- Code identifiers and comments are in English. All in-game text is in Polish, kept short, with large readable UI.
- No energy, timers, ads, purchases, accounts, or fail states.
- Use placeholders drawn in code (coloured shapes with a label) until art arrives. Real art follows the naming in plan section 10. Clock, ruler, number line, base-ten blocks and written-column layouts are drawn in code.
- Player-facing Polish text must use correct numeral agreement (1 jabłko, 2 jabłka, 5 jabłek). Wrong answers never remove stars and never show harsh "wrong" feedback.
- The Phaser 4 API is close to v3, but the renderer and filters are new. For anything non-obvious, check the v4 docs (e.g. via context7) rather than relying on v3 knowledge.
